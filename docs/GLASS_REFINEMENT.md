# ガラス表現の改良

## 実装

従来のガラス調は、元のアイコンを白黒にして透明度を下げていた。今回の変更では、macOS 26 の SwiftUI `glassEffect` をアイコンに適用する。Dock 全体を1つの `GlassEffectContainer` で囲む。絵柄は、元画像の主要な明るさとの差から透ける白い前景へ変換する。

完全透明の Dock 背景では `Glass.regular` を使う。他の背景では `Glass.clear` を使う。ポインタへの反応は `interactive` を使い、アプリまたはシステムの「動きを減らす」が有効な場合は無効にする。macOS 15〜25 では `ultraThinMaterial` を使い、透明度を下げる設定では不透明な素材に切り替える。

[Apple のカスタムビュー向け Liquid Glass の説明](https://developer.apple.com/documentation/swiftui/applying-liquid-glass-to-custom-views)を参照した。Apple の Clear アイコンと完全に同じ加工ではない。NSWorkspace から取得する画像には、[Apple のアイコン設計で使うレイヤー情報](https://developer.apple.com/design/human-interface-guidelines/app-icons)がないため、既存画像から絵柄を推定している。

## 静的レビューへの対応

Sonnet のコードレビューを1回実施した。再レビューは行っていない。実行時の懸念を含む全6項目を、以下に記録する。

| 指摘 | 対応 |
| --- | --- |
| 1. 明るい台座が白い板になる | 不透明度が一定以上の画素から、主要な明るさをヒストグラムで求める。そこからの明暗差を前景の透明度に使う。白い台座と黒い台座を CGContext の実画像で確認するテストを加えた |
| 2. ガラスの外側に追加の影がある | ガラス調のときは追加の影を透明にした。Dock 全体を隠すときの opacity は、既存の非表示の動作に必要なので残した。遷移中の描画への影響は、静的レビューだけでは判定できない |
| 3. 画素ごとの pow と全アイコンの再変換が重い | 透明度を256段の表にし、画素ごとの pow を除いた。アプリの起動と終了では、該当 URL のキャッシュだけを無効にする。NSImage の描画処理は引き続き main actor で行う |
| 4. 透明背景の視認性と素材の重なり | 透明背景には regular を使う。Dock 背景の素材は利用者が独立して設定できるため、設定自体は残す。VM では画像背景と完全透明の背景を表示して確認した。複数の壁紙とシステム素材の重なりを含む描画品質の評価は残る |
| 5. interactive と Button の併用 | 動きを減らす設定を interactive にも反映した。VM でホバー拡大、Downloads のクリック、Tab 移動後の Return と Space によるアプリ起動を確認した。非アクティブ時の右クリックでメニューが出ない問題は、パネルへの右クリック時だけアプリをアクティブにし、パネルにフォーカスを渡して修正した。Finder が前面の状態から、同じ座標の右クリックでメニューが出ることを確認した |
| 6. 負の padding による絵柄の欠け | 負の padding を除き、アイコンのフレーム全体に素材を適用した。Calendar の明るい台座と Downloads のフォルダを、VM の実表示で確認した |

## ビルドと自動テスト

2026-10-17 に、右クリックの修正後も Release ビルドが成功した。修正後の `swift test` は74件すべて成功した。これはモデルとサービスの自動テストであり、GUI の操作確認は VM 内で別に実施した。

## 画面検証の進め方

今後は、普段使っているホストのデスクトップに検証用アプリを表示しない。ホスト上では、ビルドと自動テストだけを行う。GUI の確認と撮影には専用の macOS VM を使い、VM のウィンドウや VNC ビューアーもホストに表示しない。

専用 VM は macOS 26.6.2、CPU 4個、メモリ6 GiB、画面1600×1000で起動した。ネットワークはホストとの接続だけに限定した。ホストのホーム、クリップボード、音声、USB は共有していない。ゲストには、ビルド済みのアプリと合成した背景画像、サンプル設定だけを渡した。

VM 内で管理画面を表示し、ガラス素材と背景の色が重なる実画像を取得できた。撮影には、ゲストの画面共有と、ホストのループバックだけで待ち受ける SSH トンネルを使った。Tart の実験的な VNC サーバーは、ホストの全アドレスで待ち受けることを確認したため停止した。

入力の調査では、画面共有が別のログインセッションに接続する問題と、アプリ側でプレビューの操作領域がヘッダーに重なる問題を切り分けた。ゲストの画面共有をコンソール接続に設定した。ヘッダーには zIndex を指定し、修正前は反応しなかった画面切り替えと Dock の表示切り替えが、同じ座標のクリックで動作することを確認した。存在しない SF Symbol の dock.rectangle.fill は、dock.rectangle と状態に応じた色に置き換えた。

ゲスト側だけで、通常のシステム設定を通じて入力補助の Accessibility と AppleEvents の権限を許可した。ホストの権限と SIP は変更していない。ゲストの Downloads フォルダを開く際の許可も、ゲスト内で行った。VNC クライアントの旧式認証には暗号方式の非推奨警告が出るため、通信は SSH で暗号化したループバック接続に限定している。

設定画面で通常、白黒、ガラス調を切り替え、画像背景と完全透明の背景の保存を確認した。デスクトップ用パネルでは、ホバー拡大と名前の表示、Downloads をクリックした後に Finder の Downloads ウィンドウが開くことを確認した。メニューバーの「Dock をキーボードで操作」から Tab を押し、Return と Space で Finder または Safari が前面になることを確認した。

最初の動画は、Dock が表示されていないデスクトップを撮影していたため採用していない。右クリックの修正後の最終録画では、約15秒で138フレームを取得した。25種類の画像が含まれることと、Finder のホバー拡大、名前、右クリックメニューとその終了を目視で確認した。動画は撮影時刻の間隔を維持して15 fps に変換しており、描画性能の測定には使わない。

変更前後の管理画面、外観設定、完全透明の Dock、デスクトップ用パネル、右クリックメニューと操作動画を、[検証用メディア](media/glass-refinement/)に保存する。

以前の実機画像や性能測定を、今回の修正後の結果として扱わない。仮想 GPU での確認は、実機と同一の描画品質や性能を保証しない。
